Unicast, Multicast, and Broadcast: Four Delivery Models

One receiver, a group, everyone, or the nearest instance. The differences decide how addresses map, how switches flood, and where a packet stops.

Unicast Multicast Broadcast Anycast

1. Four Answers to "Who Gets This?"

Every network conversation begins with a delivery question. Ethernet and IP answer it with four models, and the model changes the address, the forwarding behaviour, and the failure modes:

The same four receivers, four different delivery contracts.

Anycast is often left out of the list, but it is the model behind DNS root servers, CDNs, and public resolvers. It looks like unicast on the wire and is routed like unicast; the difference is that several sites advertise the same address.

2. Unicast: One to One

A unicast address identifies a single interface. An Ethernet unicast frame has a specific destination MAC; an IP unicast packet has a specific destination IP. The network forwards it along one path to one host.

  • Ethernet: I/G bit = 0, for example 00:1A:2B:3C:4D:5E.
  • IPv4: any host address outside 224.0.0.0/4 — for example 10.0.0.10.
  • IPv6: any address outside ff00::/8.

Most traffic is unicast, and unicast is the only model where a switch can make a precise forwarding decision from its MAC table. If the destination is not in the table, the frame is flooded as unknown unicast — still addressed to one host, but delivered to many ports until the address is learned. Hosts discard frames not addressed to them.

Unicast is not the same as reliable. TCP, UDP, ICMP, and QUIC all use unicast addresses; only TCP adds acknowledgements and retransmission. A unicast frame can be lost, duplicated, or delivered out of order.

3. Broadcast: One to Everyone in the Domain

A broadcast is addressed to every station in the broadcast domain. On Ethernet the destination is FF:FF:FF:FF:FF:FF; on IPv4 it is either the limited broadcast 255.255.255.255 or the subnet's directed broadcast (the all-ones host portion, such as 192.168.1.255/24).

Broadcasts exist because some problems require asking everyone:

  • ARP — "who has 10.0.0.1?" must reach every host in the subnet.
  • DHCP Discover — a client without an address has no one to ask individually.
  • Legacy name resolution — NetBIOS and similar protocols.

Broadcasts stop at routers. A router does not forward 255.255.255.255 or a subnet broadcast by default; that boundary is the broadcast domain, and on a switched network it is the VLAN. Directed broadcasts can be routed if a router is explicitly configured to allow them, which is rare because it enables amplification attacks.

Too much broadcast is a design smell. A flat VLAN with thousands of hosts spends capacity and CPU on ARP and discovery traffic that every host must inspect. Segmentation, proxy ARP, and storm control are the usual remedies.

4. Multicast: One to a Group

Multicast sends one copy to a group of interested receivers. The sender does not know or care who is in the group; hosts join and leave, and the network delivers only to the branches that have members.

  • IPv4 multicast: 224.0.0.0/4 (Class D). 224.0.0.0/24 is link-local control traffic with TTL 1; 239.0.0.0/8 is administratively scoped; 232.0.0.0/8 is source-specific multicast.
  • IPv6 multicast: ff00::/8. ff02::1 is all nodes, ff02::2 all routers.
  • Ethernet multicast: 01:00:5E plus the low 23 bits of the IPv4 group; 33:33 plus the low 32 bits of the IPv6 group.

Multicast is a membership model, not a broadcast with a filter. Hosts signal interest with IGMP (IPv4) or MLD (IPv6). Routers run a multicast routing protocol — usually PIM — to build a distribution tree, and switches use IGMP/MLD snooping to forward only to ports with members.

Common uses include IPTV, market-data feeds, software distribution, and routing protocols themselves: OSPF uses 224.0.0.5 and 224.0.0.6, VRRP uses 224.0.0.18, mDNS uses 224.0.0.251, PIM uses 224.0.0.13. Most multicast applications run over UDP because retransmitting to a group is inefficient; where reliability is required, the application adds forward error correction or a repair channel.

5. Anycast: One Address, Many Places

Anycast assigns the same address to several nodes, usually in different locations, and relies on ordinary routing to deliver each packet to the nearest one. There is no group membership and no special address range: an anycast address is a unicast address that happens to be advertised from more than one place.

  • DNS roots and public resolvers — the same address served from dozens of sites.
  • CDNs — users reach a nearby edge without choosing one.
  • IPv6 — anycast uses ordinary unicast addresses; there is no separate anycast prefix.

Anycast is stateless-friendly. If routing changes mid-flow, packets can land on a different instance, which is fine for a DNS query but can break a long-lived TCP session that expected the same state. That is why anycast services either keep flows short or synchronise state between sites.

The multicast mapping is lossy: five bits of the IPv4 group address are dropped, so 32 groups share one Ethernet address. A NIC therefore filters imperfectly and may pass frames for a group the host did not join; the IP layer discards them.

8. Broadcast, Collision, and Multicast Domains

Three domains, three boundaries:

  • Collision domain — the segment where two transmissions can collide. On a switch, every port is its own collision domain; on a hub, all ports share one.
  • Broadcast domain — the set of stations that receive a broadcast. A VLAN, or a set of VLANs bridged together. Routers do not forward broadcasts between them.
  • Multicast domain — the set of receivers and network branches interested in a group. It is defined by membership and distribution state, not by a single box.

It is possible for two hosts to be in the same broadcast domain but different multicast domains, and vice versa once multicast routing crosses a router. Treating the three as one thing leads to wrong conclusions about where traffic stops.

9. What Switches Do with Each

Frame type Switch behaviour
Known unicastForward out the learned port only
Unknown unicastFlood every other port in the VLAN until the address is learned
BroadcastFlood every other port in the VLAN
Multicast, no snoopingFlood every other port in the VLAN
Multicast, with snoopingForward only to member ports and the multicast router port
Frame to the ingress portFilter (drop)

Switches learn source MAC addresses from every frame, including multicast frames — but the source of an IP multicast frame is the sender's normal unicast MAC, not the group address. Multicast destination MACs are never learned as sources; they identify a group, not a station.

10. What Routers Do with Each

  • Unicast — route by destination prefix, rewriting the Layer 2 header at each hop.
  • Broadcast — terminate it. Routers do not forward 255.255.255.255 or subnet broadcasts by default; that is what makes a router the edge of a broadcast domain.
  • Multicast — only if multicast routing is enabled. PIM builds the tree, RPF checks the incoming interface, and IGMP/MLD tracks members on the last hop.
  • Anycast — route normally. Several sites advertise the same prefix; the routing table picks the closest according to the protocol's metric.

A router that receives a multicast packet without multicast routing configured will drop it. It does not fall back to flooding, and it does not treat it as broadcast.

11. Design and Troubleshooting

  • Watch the broadcast rate. A few percent of link capacity is normal in a healthy access VLAN; a sustained climb suggests a loop, a duplicate address, or a subnet that grew too large.
  • Watch unknown unicast. Persistent flooding means the MAC table is not learning, is full, or is aging too fast.
  • Enable IGMP snooping where multicast matters. Without it, every multicast stream is broadcast to the VLAN. Snooping also needs a querier; without one, group state may never form.
  • Scope multicast. Keep local control traffic at TTL 1, use 239.0.0.0/8 for internal groups, and filter at boundaries.
  • Use storm control as a backstop for broadcast, multicast, and unknown unicast — not as a substitute for correct design.
  • Document anycast prefixes. Know which sites advertise them and how withdrawal behaves, because convergence changes which instance serves a flow.

12. Three Cases

Case A: the VLAN that grew too large

A campus put 2,000 users on one flat VLAN. Periodic slowdowns affected everyone, not just one application.

EvidenceReading
Broadcast rate8–12% of access-link capacity at peak
Top talkersARP and legacy discovery, not user data
SubnetA single /16 with no segmentation

Splitting the floor into per-department VLANs cut broadcast traffic by an order of magnitude and made the ARP cache sizes manageable. Broadcast is cheap per frame and expensive per host.

Case B: the video stream on every port

A new IPTV feed saturated an access switch. Every port carried the stream, including ports with no viewers.

EvidenceReading
Multicast group4 Mb/s continuous on all 48 ports
IGMP snoopingDisabled on the VLAN
QuerierNone configured

Enabling snooping and a querier reduced the stream to the ports that had joined and the uplink toward the source. The group was working exactly as designed; the switch was treating it as broadcast.

Case C: the anycast site that went away

A DNS service advertised the same address from two data centres. During a maintenance window, one site withdrew its route.

EvidenceReading
RoutingPrefix reconverged to the surviving site
New queriesServed normally after convergence
Long-lived TCP sessionsA few reset when packets moved to a different instance

That is the anycast trade-off in one incident: excellent availability for short transactions, no stickiness for long flows. The design answer is stateless service, short flows, or shared state — not a longer TTL.

13. Exam Traps

  • "Routers forward broadcasts." They do not, by default; broadcasts stop at the broadcast domain.
  • "Multicast uses TCP." It is almost always UDP; there is no ACK or retransmission at the multicast layer.
  • "IGMP is a multicast routing protocol." IGMP manages group membership; PIM and similar protocols route multicast.
  • "Multicast MAC uses all 28 bits of the IPv4 group." Only the low 23 bits are mapped; 32 groups share one MAC.
  • "Anycast is a separate address type." It uses ordinary unicast addresses shared by multiple sites.
  • "Unknown unicast is a broadcast." It is addressed to one host and flooded only because its location is unknown.
  • "Broadcast domain equals collision domain." A switch port is a collision domain; a VLAN is a broadcast domain.
  • "IPv6 uses broadcast." IPv6 has no broadcast; it uses multicast, including all-nodes ff02::1.
  • "255.255.255.255 can be routed." It is link-local by definition; routers do not forward it.
  • "Multicast guarantees delivery to every member." It is best effort, like all Ethernet and IP delivery.

14. Key Takeaways

  • Unicast is one-to-one, broadcast is one-to-all in a domain, multicast is one-to-group, anycast is one-to-nearest.
  • Broadcast stops at the router and at the VLAN boundary; multicast can cross routers only with multicast routing configured.
  • Ethernet maps broadcast to FF:FF:FF:FF:FF:FF and multicast to 01:00:5E / 33:33 prefixes.
  • Multicast is a membership model: IGMP/MLD for hosts, PIM for routers, snooping for switches.
  • Anycast is routing, not addressing: the same unicast prefix advertised from several places.
  • Unknown unicast is flooded, but it is still unicast; the destination host is the only one that should accept it.
  • Broadcast, collision, and multicast domains have different boundaries and different failure modes.
