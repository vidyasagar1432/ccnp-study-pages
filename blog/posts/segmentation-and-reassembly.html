Segmentation and Reassembly: TCP MSS, IP Fragmentation, and MTU

Applications think in byte streams; links think in frames of limited size. This article explains who splits the data, where it is put back together, and why MTU problems cause some of the hardest-to-diagnose outages on real networks.

TCP IP MTU Fragmentation Fundamentals

1. Two Different Jobs With Similar Names

"Segmentation and reassembly" gets used loosely, but two separate mechanisms are involved, and confusing them is the source of most exam mistakes:

  • TCP segmentation happens at Layer 4. The sender divides an application byte stream into TCP segments sized to fit the path MTU, and the receiver reassembles those segments into an ordered byte stream. This is normal, expected, and invisible to the application.
  • IP fragmentation happens at Layer 3. When a datagram is larger than the next link's MTU, IPv4 can split it into fragments that are reassembled only at the final destination. This is an exception path, and it is usually something you want to avoid.

In short: TCP segmentation is the designed behavior; IP fragmentation is the fallback. A healthy network relies on the first and rarely sees the second.

2. Why Size Limits Exist

Every link has a Maximum Transmission Unit (MTU) — the largest IP packet (header plus payload) that can be carried in one Layer 2 frame. The classic Ethernet MTU is 1500 bytes. Frames larger than the link MTU cannot be transmitted as a single unit, so something has to give:

  • The transport layer can send smaller segments (TCP does this).
  • The network layer can split the packet into fragments (IPv4 can, IPv6 largely cannot).
  • Or the packet can be dropped with an ICMP error that tells the sender to shrink.

The third option is what modern networks prefer, because it lets the sender adapt without creating reassembly work for the receiver.

3. TCP Segmentation in Depth

TCP presents a byte stream to the application. It has no concept of your application's message boundaries — if you write 10,000 bytes to a socket, TCP decides how many segments that becomes based on the MSS, the congestion window, and the receiver's advertised window.

Maximum Segment Size (MSS)

MSS is the largest TCP payload a host is willing to receive in a single segment. It is not negotiated as a minimum; each side advertises its own MSS in the SYN, and each side uses the other's value when sending.

MSS = MTU - IP header - TCP header
Scenario Calculation MSS
IPv4 over Ethernet (MTU 1500)1500 − 20 (IPv4) − 20 (TCP)1460
IPv4 with TCP timestamps/options (TCP header 32)1500 − 20 − 321448
IPv6 over Ethernet (MTU 1500)1500 − 40 (IPv6) − 20 (TCP)1440

Note how quickly encapsulation erodes the usable payload. This is why tunnels and overlay networks so often need an explicit MSS adjustment.

How the receiver reassembles

TCP reassembly is driven by sequence numbers. The receiver tracks the next expected byte, places out-of-order segments into a receive buffer, and delivers contiguous data to the application in order.

  • In-order segment — appended to the buffer and immediately available to the application.
  • Out-of-order segment — held until the gap is filled (a "hole").
  • Missing segment — detected by duplicate ACKs or a retransmission timeout, then retransmitted.
  • Selective ACK (SACK) — tells the sender exactly which ranges arrived, so only the hole is retransmitted instead of everything after it.

The cost of this design is head-of-line blocking: data that arrived successfully cannot be delivered until the missing bytes arrive. That is the right trade-off for a file transfer and the wrong one for real-time media, which is why protocols like QUIC move reliability above UDP and avoid blocking unrelated streams.

Segmentation offload (why captures look weird)

Modern NICs perform TSO/GSO (TCP Segmentation Offload / Generic Segmentation Offload) on the sender and GRO/LRO on the receiver. The host hands the NIC a large buffer and the hardware splits it into MSS-sized frames. If you capture traffic on the sending host, you may see "segments" far larger than the MSS, or checksums marked as incorrect. Both are artifacts of offload, not faults. Capturing on the wire (a SPAN port or TAP) shows the real frames.

4. IP Fragmentation in Depth

IPv4 fragmentation happens when a packet must traverse a link whose MTU is smaller than the packet size, and the packet is allowed to be fragmented (the DF bit is clear). The original packet is split, and the receiver reassembles the pieces using fields in the IPv4 header.

The IPv4 fields that make it work

Field Size Role in fragmentation
Identification16 bitsSame value on every fragment of one original datagram; used to group them at the receiver.
Flags — DF1 bitDon't Fragment. If set and the packet exceeds the MTU, the packet is dropped and an ICMP error is returned instead of fragmenting.
Flags — MF1 bitMore Fragments. Set on every fragment except the last one.
Fragment Offset13 bitsPosition of this fragment's payload in the original datagram, measured in 8-byte units.
Total Length16 bitsLength of this fragment, not the original datagram.

Two rules follow from the offset encoding: every non-final fragment's payload must be a multiple of 8 bytes, and the maximum offset (8191 × 8) caps the original datagram at 65,535 bytes, consistent with the 16-bit Total Length field.

Worked example

Take an IPv4 datagram of 4000 bytes total (20-byte header + 3980 bytes of data) crossing a link with MTU 1500.

  • Payload per fragment = 1500 − 20 = 1480 bytes (already a multiple of 8).
  • 3980 ÷ 1480 = 2 full fragments plus 1020 bytes remaining.
  • Fragment 1: offset 0, MF=1, total length 1500.
  • Fragment 2: offset 185 (1480 ÷ 8), MF=1, total length 1500.
  • Fragment 3: offset 370 (2960 ÷ 8), MF=0, total length 1040.

Each fragment carries a copy of the original IP header (with adjusted Total Length, Flags, and Offset), so the overhead is 20 bytes per fragment. All three must arrive for the datagram to be reassembled; if any is lost, the entire original datagram is discarded and TCP (or the application) must retransmit.

IPv4 fragmentation: offsets count 8-byte units, MF marks all but the last fragment, and reassembly is the destination's job.

5. IPv6 Changed the Rules

IPv6 removes fragmentation from the forwarding path. Routers do not fragment packets; only the source host may do so, and it must use a Fragment extension header containing an identification value, a fragment offset, and an M (more fragments) flag.

  • Every IPv6 link is required to support at least 1280 bytes, so the source can always send 1280 bytes without fragmenting.
  • Hosts are expected to perform Path MTU Discovery and send packets that fit.
  • A router that cannot forward an oversized packet returns ICMPv6 Packet Too Big (Type 2) and drops it.
  • The IPv6 header has no DF bit — the absence of router fragmentation makes DF unnecessary.

This design is cleaner, but it makes correct ICMPv6 filtering even more important: if Packet Too Big messages are blocked, IPv6 hosts cannot discover the real path MTU and will keep retrying packets that never fit.

6. Path MTU Discovery (PMTUD)

PMTUD is how a sender learns the smallest MTU along a path without guessing.

  1. The sender sets DF=1 (IPv4) and sends packets at the local MTU.
  2. A router on a smaller-MTU link cannot forward the packet, so it drops it and returns ICMP Type 3 Code 4 — "fragmentation needed and DF set" — including the next-hop MTU in newer implementations.
  3. The sender lowers its path MTU estimate and retransmits. The process converges quickly and is cached per destination.
  4. IPv6 works the same way with ICMPv6 Packet Too Big.

The black hole problem

If a firewall blocks those ICMP errors, the sender never learns and keeps sending full-size packets. Small packets (pings, DNS, TCP handshakes) succeed, but large ones vanish silently. The classic symptoms:

  • SSH connects and lets you log in, then hangs the moment you run a command with a large output.
  • A website's homepage loads but large images stall.
  • Ping with small payload works; ping with a large payload fails.
  • TLS handshakes complete, then the first large application response never arrives.

This is a PMTUD black hole, and it is one of the most common "it works, but only sometimes" tickets in enterprise networks.

7. MTU, MSS, and Encapsulation Overhead

Tunnels add headers, which reduces the payload a given physical MTU can carry. You either raise the underlying MTU, lower the tunnel MTU, or clamp MSS. The table below shows typical overheads:

Encapsulation Typical added bytes Effective MTU on 1500 Suggested TCP MSS (IPv4)
802.1Q VLAN tag41500 (frame becomes 1522)1460
GRE (no options)24 (20 outer IP + 4 GRE)14761436
GRE with key2814721432

VXLAN50 (14 Eth + 20 IP + 8 UDP + 8 VXLAN)14501410

Two design choices are common: set the tunnel interface MTU to 1500 − overhead and let PMTUD handle the rest, or keep the tunnel MTU at 1500 and clamp MSS on tunnel traffic so TCP never emits a segment that will not fit after encapsulation. Clamping is the pragmatic fix when ICMP is filtered somewhere in the path.

Jumbo frames (MTU 9000) reduce per-packet overhead in data centers, but only work if every device in the path — including switches, storage, and virtual switches — agrees. A single 1500-byte device in a jumbo path produces exactly the black-hole behavior described above.

8. Diagnosing MTU and Fragmentation Problems

Step 1: Find the path MTU

# Linux: discover path MTU by probing sizes with DF set
ping -M do -s 1472 10.0.0.5        # 1472 + 28 = 1500 byte packet
ping -M do -s 1400 10.0.0.5

# Linux: report the MTU along the path
tracepath 10.0.0.5

# Windows
ping -f -l 1472 10.0.0.5

# macOS
ping -D -s 1472 10.0.0.5

Note the arithmetic: the -s/-l value is the ICMP payload, so for IPv4 add 8 (ICMP header) + 20 (IP header) = 28. A 1472-byte payload gives exactly 1500 bytes on the wire.

Step 2: Check interface MTU and counters

# Cisco IOS / IOS XE
show interfaces GigabitEthernet0/1
show ip interface GigabitEthernet0/1
show ip traffic | include fragment
show interfaces Tunnel0

# Linux
ip link show
ip -s link show eth0

# Windows
netsh interface ipv4 show subinterfaces

Step 3: Fix it at the right place

# Cisco: clamp TCP MSS on a tunnel or interface (IPv4)
interface Tunnel0
 ip tcp adjust-mss 1400

# Cisco: lower the interface MTU instead
interface Tunnel0
 ip mtu 1400

# Linux: lower the MTU
ip link set dev eth0 mtu 1400

# Linux: enable PMTUD probing as a fallback
sysctl -w net.ipv4.tcp_mtu_probing=1
Symptom Likely cause Action
Small pings succeed, large pings fail MTU too small somewhere, DF prevents fragmentation Lower MTU or clamp MSS; verify ICMP is allowed

9. Security and Operational Notes

  • Fragment attacks — overlapping fragments (teardrop-style) and tiny fragments have historically confused reassembly. Modern stacks handle overlaps conservatively, and firewalls commonly drop non-first fragments or normalize them.
  • Reassembly resource use — a host must buffer fragments until the datagram completes or a timer expires (commonly 30–60 seconds in IPv4). Floods of partial datagrams can exhaust those buffers, which is why many networks rate-limit or block fragments at the edge.
  • Firewall policy — blocking all ICMP breaks PMTUD. Permit at minimum ICMP Type 3 Code 4 (IPv4) and ICMPv6 Type 2, ideally rate-limited.
  • Load balancing — non-first fragments lack Layer 4 headers, so some load balancers and ACLs treat them differently. Another reason to keep packets unfragmented.
  • Captures — offload can make a host capture disagree with the wire. Always confirm where the capture was taken before concluding a segmentation bug exists.

10. Key Takeaways

  • TCP segments; IP fragments. Segmentation is routine, fragmentation is a fallback.
  • MSS = MTU − IP header − TCP header. 1460 for IPv4/Ethernet, 1440 for IPv6/Ethernet.
  • Reassembly by sequence number lets TCP rebuild the byte stream, at the cost of head-of-line blocking.
  • IPv4 reassembly happens only at the destination, uses Identification/DF/MF/Offset, and loses the whole datagram if one fragment is lost.
  • IPv6 forbids router fragmentation and depends on PMTUD and ICMPv6 Packet Too Big.
  • Tunnels shrink the usable MTU. Account for GRE, IPsec, VXLAN, PPPoE, and MPLS overhead — then clamp MSS or lower the MTU deliberately.
  • "Works small, fails large" is the signature of an MTU problem. Test with DF set and verify ICMP is not being dropped.
