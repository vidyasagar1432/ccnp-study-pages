OSI vs TCP/IP Side by Side: Layers, Protocols, and Where They Differ

Two models, one network. Here is how the seven OSI layers line up against the four TCP/IP layers, what changes at each boundary, and which vocabulary to use when.

OSI TCP/IP Comparison Protocols Fundamentals

1. Two Models, Two Different Jobs

The OSI and TCP/IP models are usually taught as rivals. They are not. They were built for different purposes, and that purpose explains every difference between them.

  • OSI is prescriptive. ISO designed a general framework for any network, before the protocols existed. It says what each layer should do, independent of any implementation. That is why it has fine-grained layers for presentation and sessions.
  • TCP/IP is descriptive. It documents the protocol suite that was already running the ARPANET and later the internet. It says what the protocols actually do, which is why three OSI layers collapse into one and two collapse into another.

So the honest summary is: OSI is a reference model; TCP/IP is an implementation model. One is a blueprint, the other is a photograph of the building.

2. The Layers, Side by Side

Every OSI layer has a home in TCP/IP, but the mapping is many-to-one at the top and bottom.

4. The Comparison That Matters

Most "OSI vs TCP/IP" tables list the layer counts and stop. The differences that actually matter are about intent and adoption:

Notice the pattern: OSI won the vocabulary, TCP/IP won the deployment. When an engineer says "Layer 2 switch" or "Layer 7 firewall," they are using OSI numbering to describe TCP/IP equipment. That mixture is normal and correct.

5. Where the Mapping Breaks

The one-to-one mapping works for the textbook layers and fails for real protocols. These are the cases worth knowing:

Protocol Mapped to Why it does not fit cleanly
ARPNetwork Access (L2)Carries an IP address but never crosses a router; often called Layer 2.5
ICMPInternet (L3)Rides directly in IP with no ports, yet is consumed by application tools
TLSApplication boundaryEncrypts application data but runs over TCP; OSI calls this presentation
BGPInternet (routing)Uses TCP port 179, so it looks like an application while building the routing table
QUICTransportRuns over UDP and bundles reliability, TLS 1.3, and streams into one protocol
MPLSBetween L2 and L3Forwards on labels rather than IP addresses; "Layer 2.5" again
GRE / IPsecInternetEncapsulate a whole packet inside another, effectively stacking the model

This is not a flaw in either model. It is what happens when a clean abstraction meets protocols designed to solve several problems at once.

6. Same Encapsulation, Different Labels

Both models describe the same wrapping process. The only difference is how many named steps you count on the way down.

With a 1500-byte MTU, those headers leave 1460 bytes for TCP payload. The models disagree about how many layers you draw; they agree exactly about how many bytes you lose.

7. One Fault, Two Vocabularies

Troubleshooting is where the models earn their keep. The same problem gets described differently depending on which model you are using — and either description is fine, as long as it narrows the search.

Pick one model and stay in it for the duration of the incident. Mixing "it is a Layer 4 problem" with "check the Network Access layer" mid-conversation is how teams lose ten minutes.

8. Which Model Should You Use?

  • Use OSI naming for design and documentation. "Layer 2 access, Layer 3 core, Layer 4 load balancing, Layer 7 inspection" is precise and vendor-neutral.
  • Use TCP/IP when you touch packets. Captures, header fields, socket states, and routing tables are organized by the protocols, not the reference model.
  • Use either for troubleshooting, but map the fault deliberately: physical → framing → reachability → port → application.
  • Use both for exams. CCNP questions assume you can translate in either direction, including the boundary cases.

9. Myths That Cost Marks

  • "OSI and TCP/IP are competing standards." They are a reference model and an implementation model. Only the protocols competed, and TCP/IP won.
  • "OSI is obsolete." Its protocols lost, but its layer vocabulary is used every day — L2, L3, L4, L7.
  • "OSI transport is reliable; TCP/IP transport is not." Both define connection-oriented and connectionless services. IP is best-effort; TCP is reliable; OSI had equivalents of both.
  • "TCP/IP's application layer is OSI Layer 7." It covers Layers 5, 6, and 7.
  • "TCP/IP has a hidden session layer." No. Session state lives in the application or in TCP connections.
  • "ARP is a Layer 3 protocol because it handles IP addresses." It is conventionally Layer 2/Network Access; it does not route.
  • "There are only two models." Many courses teach a five-layer hybrid (Physical, Data Link, Network, Transport, Application). It is a teaching compromise, not a third standard.

10. Exam Traps

  • Questions asking "which layer?" usually expect the OSI number, even when the protocol is TCP/IP.
  • "Which TCP/IP layer handles encryption?" — Application, because TCP/IP has no presentation layer.
  • "Which layer does a switch operate at?" — Layer 2 for a classic switch; a Layer 3 switch routes at Layer 3.
  • "Where does a firewall operate?" — usually Layers 3–4; a next-generation firewall inspects up to Layer 7.
  • Do not say TCP/IP has seven layers or OSI has four. The counts are the most-tested fact in this topic.
  • BGP is a routing protocol that runs over TCP. If the question asks about its function, it belongs to the Internet layer; if it asks about its transport, it is TCP port 179.

11. Key Takeaways

  • OSI is a 7-layer reference model; TCP/IP is a 4-layer implementation model.
  • OSI 7–5 → Application, 4 → Transport, 3 → Internet, 2–1 → Network Access.
  • The lower four OSI layers map one-to-one; the top three collapse into one.
  • Encapsulation is identical in both models — only the number of named steps differs.
  • Boundary protocols (ARP, TLS, ICMP, BGP, QUIC, MPLS) are where mapping questions get interesting.
  • OSI supplies the vocabulary; TCP/IP supplies the protocols. Fluent engineers use both.
